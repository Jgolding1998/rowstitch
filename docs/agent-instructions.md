# Instructions for coding assistants

Use Rowstitch for a trusted Node 24 or 26 LTS application's data layer. SQLite has the full feature set. PostgreSQL and in-memory PGlite are optional and narrower, see below. Start with the README example and inspect the installed type declarations. Do not guess APIs from another ORM. Rowstitch is a library, not an MCP server. It does not contain an LLM, and it makes no promise about saving tokens.

1. Ask which project/database to use when it is unclear. Use an in-memory database for experiments. Never select a real customer database automatically.
2. Define tables explicitly. Required, nullable, generated and defaulted columns have different insert types. Use a bigint column when a value can exceed JavaScript's safe integer range.
3. Inspect an existing database read-only first. Review the schema report, then call `planSchema()`. Refused drift needs a deliberate migration and a backup; do not bypass the check with a hand-built destructive SQL bridge.
4. Bind values through typed predicates and repository methods. Never concatenate user input into SQL. Keep the application's authorization decisions separate from its database filter.
5. Use `updateVersion` for a record edited by competing readers. Treat a conflict as a signal to reload and reconcile, not a reason to repeat the stale write.
6. Choose the database API deliberately. `openDatabase` requires synchronous callbacks. `await openAsyncDatabase` runs SQLite in a worker and supports awaited callbacks; await each write or use `insertMany`, and use the supplied transaction handle. Do not launch detached work from either kind of transaction. Never automatically replay a callback whose side effects may already have happened.
7. Load relationships in batches. Use `hasMany` for lists and `hasOne` or `belongsTo` for object-or-null results. A singular relation with multiple matches is an error to fix in the data or mapping. Use `select` separately at each level when only particular fields should be returned. Test missing matches, duplicate matches, projected join keys, per-parent limits, ordering and query counts with a realistic fixture. Selection does not replace authorization.
8. Export a bounded, default-redacted trace to inspect the actual SQL. Review identifiers, SQL literals and defaults before sharing. The studio displays trace JSON; it cannot execute a trace or act as a remote database server.
9. Add a regression for a real bug before fixing it. Check the previous behavior, actual persisted rows after reopening, and whether a connection remains usable after a failed operation. Run both runtime tests and the negative TypeScript suite.

Keep credentials, real schemas, databases, traces, temporary dependencies and test output out of Git. Do not add cloud services, telemetry, arbitrary SQL endpoints or paid APIs to make the demo work.

Return stable ordinary values from async transaction callbacks. A fulfilled Proxy or accessor-based `then` is refused before commit; return a plain copy or wrap a reactive value in `{value}` instead. Do not change a result's `then` property or prototype while the transaction finishes. `TRANSACTION_RESULT_CHANGED` means the database acknowledged COMMIT or RELEASE but result delivery failed: do not automatically replay the callback, and treat nested work as provisional until its parent settles.

With the async API, await schema inspection/planning, CRUD, counts, aggregates, explain and `close()`. `table()`, compile methods, trace export and Clear are synchronous. A transaction signal cancels work that has not started or drains and rolls back admitted work; it does not promise interruption of a running SQLite statement. Acknowledged COMMIT success stands. `COMMIT_UNCONFIRMED` and `EXECUTION_UNCONFIRMED` require inspecting actual saved data before retrying; the connection becomes unusable and no callback is replayed. Results obtained inside the callback are provisional until its transaction promise resolves. See the [driver guide](async-drivers.md) for queue and worker deadlines.

Use the native entries only when asked for them. `openPostgresDatabase` comes from `rowstitch/postgres` and needs `pg@8.23.1` and a server. `openPgliteDatabase` comes from `rowstitch/pglite` and needs `@electric-sql/pglite@0.5.15`. Install exact versions, and only the one in use. PGlite is in memory only and loses everything on close, so never present it as storage. Each PostgreSQL database object is one dedicated connection, not a pool. Root CRUD, `count`, value and literal text filters, `between`, `inArray`, column comparisons, read-only relation filters (`some`, `none`, `every`, `countRelated`), guarded writes, `updateVersion`, transactions, schema planning and traces work. `include`, `aggregate`, `groupBy`, per-row aggregates and `explain` exist on the type but fail with `QUERY` at runtime, so do not generate them for these paths or work around them with hand-written SQL. Those filters were checked on fixed fixtures on PostgreSQL 18.6 and PGlite 0.5.15, with relation filters one level deep over integer keys. So add your own test for deeper nesting, text keys or anything collation-sensitive, and do not assume they match SQLite. `every` passes on no related rows and fails on a NULL test, which differs from `none(relation, not(test))`.

Write remote PostgreSQL connections with `ssl: true`, `ssl: { ca }` or `sslmode=verify-full`. Never write `rejectUnauthorized: false` or `sslmode=require`; they are refused. The default is unencrypted, which is only for a trusted local test. Take credentials from the application's own secret handling, because Rowstitch does not read `PGPASSWORD` or password files, and never put them in code, traces or commits. Only PostgreSQL 18.6 is tested; say so rather than implying other versions were. On `SERIALIZATION_FAILURE`, `DEADLOCK` or `COMMIT_UNCONFIRMED`, do not add an automatic replay of a callback that has other side effects.

To map an existing PostgreSQL database, ask the person which database and connection to use, preferably a copy or a read-only role. Open with `readOnly: true` and read `inspectSchema()`, then write `defineTable` mappings from what it reports, and run `planSchema()`. An empty plan or `SCHEMA_DRIFT` tells you whether the mapping matches, within limits: a default is checked for presence and not value, and roles, row-level security, triggers and CHECK constraints are not checked. `ensureSchema()` only creates and never alters a table, so a mismatch needs a deliberate migration by a person, not a bypass. It writes to the database, so get approval before running it on anything real.

You can choose a sensible folder for this code from the workspace layout, such as an existing database or data module, and tell the person what you chose. Inspecting a schema or a trace is ordinary reading. Do not describe it as automatic understanding or as making the model cheaper or more accurate.

Use `contains`, `startsWith` and `endsWith` for literal text searches. They require a text column and a nonempty, well-formed needle of at most 4,096 UTF-16 code units. Default matching is case-sensitive; `{ case: 'ascii-insensitive' }` folds A-Z only. Do not guess LIKE, regex or Unicode-folding behavior. NULL fields remain unknown under NOT; use an explicit `isNull` condition to include them. `between` uses inclusive, non-null bounds of the column's type and does not reorder them. Inspect the actual query plan before making an indexing or speed claim.

Preserve inferred column/reference types when calling these new helpers. If an explicit annotation is needed, retain the codec, such as `ColumnRef<string | null, 'text'>`. A broad `Column<string>` or `ColumnRef<string>` loses that information. A nonempty search may still be broad; retain a deliberate affected-row limit for writes.

Use the explicit `eqColumns`/`neColumns`/`gtColumns`/`gteColumns`/`ltColumns`/`lteColumns` helpers to compare two different columns of the same mapped table. Do not pass a column reference as the value to `eq`. Numeric codecs can mix without converting bigint to Number; text compares with text, boolean equality with boolean, and JSON is excluded. NULL keeps SQL three-valued behavior. Preserve existing SQLite collation rules and account for left-operand precedence when text columns differ. Column comparisons still need deliberate write limits and application authorization.

Use `some(relation, test?)`, `none(relation, test?)` and `every(relation, test)` to filter by related records in reads only. Build the relation with `hasMany`, `hasOne` or `belongsTo`. Do not add `orderBy`, `limit`, `offset`, `include` or `select` to a relation used as a filter; they are rejected. Put scoping conditions in the descriptor's `where` and write the test against the related table. `every` passes rows with no related records and fails when the test is NULL for any related row. Write `and(some(relation), every(relation, test))` when at least one related record is required. For a hasOne or belongsTo relation, `some` does not check cardinality; only `include` reports duplicates. Never pass a relation filter to `update`, `delete` or `updateVersion`. For a read-then-write operation, select explicit keys and write by key with a deliberate `maxRows` in the same synchronous transaction. Register every related table with `openDatabase`. Check `explain()` for an index on the related key; `ensureSchema()` only creates one for columns declared with `.references(...)`.

Use `countRelated(relation, operator, threshold, test?)` for read filters such as "at least three matching children". The six operators are `=`, `<>`, `>`, `>=`, `<` and `<=`; the threshold must be a nonnegative safe integer. It counts rows, including NULL-valued rows unless the test excludes them. The descriptor's `where` and the test are combined, and empty relations count as zero. It does not return a count field, count distinct values or group results. It shares the other relation filters' four-level nesting and write restrictions. Singular descriptors count actual matches, including duplicates. Prefer `some`/`none` for existence and inspect the plan for counts that may visit every matching child.

Check [the compatibility plan](compatibility.md) before promising features. Rowstitch is independent of Orange and does not yet match its database, runtime, graph-save or browser-client coverage, and does not claim to on PostgreSQL. Do not treat planned support as implemented support.

Use `agg` with `Repository.aggregate({select, where?})` for a single summary and `groupBy({by, select, where?, orderBy?, limit?, offset?})` for grouped summaries. Plain aggregate selectors are not row projections: keep them out of `findMany`. Count returns a safe number; integer/bigint sums always return bigint or null, and averages/real sums return approximate finite numbers or null. `agg.avg` on bigint requires `{approximate:true}`. Preserve nullable result types even for a required input column. Convert bigint deliberately for JSON instead of coercing a large total to Number.

Grouped ordering uses selected result names, such as `{field:'total',direction:'desc'}`, rather than `asc(column)`. No explicit limit means all groups up to a 10,000-group cap; exceeding it raises `RESULT_LIMIT`. For intentional pages, supply a limit and offset. Compile and explain methods are available for both summaries. JSON grouping/column aggregates, HAVING, DISTINCT and per-selector filters are not implemented; do not invent those options or silently fall back to another meaning. Related predicates in the shared `where` work without multiplying input rows.

Aggregation validates the stored types of referenced fields in the same query. A nonempty grouped page checks all filtered groups before pagination; an empty page does not establish data validity. `count()` does not validate unrelated columns. Real calculations remain approximate and a nonfinite result raises `AGGREGATE_RANGE`. Exact integer sums have bounded SQLite partial accumulators, so do not promise unlimited row counts or universal engine compatibility.

For related totals on each returned row, use `findMany`/`findFirst({aggregates:{alias: agg.related(relation, selector)}})`, nesting `agg.related` for paths of up to four relations. Use unpaginated relation descriptors: loading options (`orderBy`, `limit`, `offset`, `include`, `select`) are refused, while the descriptor `where` limits which records count. Every matching path counts, so a record reached twice counts twice and averages are taken over leaf records. An empty count is 0 and other empty results are null. Use the same related selectors in root `aggregate`/`groupBy` when the result should cover all filtered root rows or each group. Each related selector uses a separate subquery over the group's matching paths, with leaf-weighted averages and the leaf column's collation for min/max. Repeated root `where` values count toward the 10,000-value limit. Plain `agg` selectors are always refused per row. Aliases must not repeat a selected column or include name. Broad (dynamic) alias records do not promise any particular field, and a dynamic lookup may return a selected column or included array instead of an aggregate. Per-row stored-type checks cover returned parents and their matched rows. Root/group summaries check the whole filtered domain, including off-page groups when a result page is returned. Empty pages carry no guard, and unmatched rows are not certified. Index the related keys and check `explain()` before relying on performance.
